# Context and output budgets

Task 3.4 applies two bounds before a live reply. Laravel reads only the acting user's owned conversation, up to the newest 50 messages. It removes the oldest messages if the exact signed JSON body would exceed the engine's 1 MiB admission limit. It never shortens the pending question. If that question alone cannot fit, the run endpoint returns `422 context_too_large`.

The engine resolves the conversation's selected Pi model before sizing the prompt. `maxInputTokens` defaults to 32,000 and `maxOutputTokens` to 4,096 in the server-created run snapshot. Configure them through `ASSISTANT_MAX_INPUT_TOKENS` (1,024–200,000) and `ASSISTANT_MAX_OUTPUT_TOKENS` (1–32,000) in Laravel. The engine caps output again by the model's advertised `maxTokens`, the hard 32,000 ceiling and half its `contextWindow`. It reserves that output plus the larger of 256 tokens or 2% of the model window before accepting input.

Input is measured conservatively as the UTF-8 byte length of the serialized Pi context plus 512 for framing. This includes the system prompt, offered tool schemas and messages. The engine removes oldest whole messages until the context fits, keeping the newest question. It checks the resulting context again immediately before **every** model request, since tool results and previous answer text can grow it. If the newest question cannot fit, or a later round grows beyond the budget, the run ends with `run.failed` / `context_limit_exceeded` before another provider request. Partial deltas are never saved as a final answer.

This is a deliberately conservative cross-provider estimate, not a provider tokenizer or a promise of exact billing tokens. Provider-specific wrappers can add tokens after Pi's request boundary; the reserved margin reduces that risk. Measure actual usage and context behavior with each production model before raising these bounds. The existing four model rounds, six tool calls, 180-second deadline, per-tool timeout/result cap and 200,000-unit aggregate answer cap still apply. Simulation follows its deterministic path and does not call a live model.

Controlled tests cover recent-answer recall with older history removed, a current question rejected before a provider request, a small selected model window, output cap forwarding, and growth after a tool call. They do not establish a new live-provider acceptance result; the owner's current ChatGPT connection requires sign-in after a recorded provider refusal. See [validation](validation.md) and [provider status](provider-matrix.md).
